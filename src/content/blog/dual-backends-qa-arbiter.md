At some point on the asset-conversion pipeline I'd been building, we needed a second
implementation. The first one drove a DCC application ([Houdini](https://www.sidefx.com)) to do
the heavy lifting — great for artist-editable material networks and a validated production path,
but a heavy dependency to carry everywhere. So I wrote a **second backend in pure Python**, with a
vendored [USD](https://openusd.org) / MaterialX / [OpenImageIO](https://openimageio.readthedocs.io)
runtime, that produces the same output with no DCC installed.

Writing the second backend was the easy part. The real question was the one that keeps you up at
night: **how do you actually know the two produce the same thing?**

## The obvious answer is a trap

The tempting approach is to keep a "gold" set of known-good outputs from the first backend and
diff the second backend against it. It feels rigorous. It isn't — not here.

Our gold outputs had been generated by an older texture path (a GPU route) whose pixels differ,
at the byte level, from a fresh CPU run — different resampling, different rounding, none of it
visible or meaningful to any downstream consumer. So a pixel diff against gold would light up red
on outputs that were perfectly correct, and, worse, bury a genuine regression somewhere in that
sea of false positives. **Diffing against stale gold doesn't measure correctness; it measures
how old your gold is.**

## Reframing "correct"

The move that unlocked it was to stop asking "does backend B match backend A's pixels?" and start
asking "**does the output satisfy the rules a consumer actually cares about?**" — and to make an
**independent QA gate** the authority on that question.

Three properties made the gate trustworthy:

1. **It runs after conversion, on the output alone.** QA reads the produced files from disk and
   judges them for completeness, correctness, and compatibility. A pass means *ship-ready,
   regardless of which backend produced it.* The gate doesn't know or care which backend ran.

2. **It does not import the converter.** This is the subtle, crucial part. QA re-derives its
   expectations — expected resolutions per tier, which material a given asset should get, the
   colour-space policy, the naming and metadata contract — from *its own* constants, copied and
   cited rather than imported. If the converter and QA ever disagree about a rule, that's a
   **visible test failure, not a silent agreement.** A gate that imports the thing it's checking
   can only ever confirm the code does what the code does.

3. **It judges the converter, not the source data.** Many rules are *source-differential*: a
   texture missing at the source is flagged for human review, not counted as a converter failure.
   To make that distinction honestly, QA reads the source metadata through the *same* repair path
   the converter used — so both agree on what the input actually was before either passed judgment.

Findings carry a severity (error / warn / info); the ship gate is simply "no errors." A separate
pass / review / fail verdict routes the genuinely ambiguous cases — usually pre-existing
source-data problems — to a person instead of pretending the machine can decide.

## Parity that holds by construction, not by luck

With QA as the arbiter, backend parity stops being something you *test for* after the fact and
becomes something you *build in*. The two backends share the pieces that decide behaviour — the
same pure-logic module for colour-space rules, the same texture-conversion routine — and the newer
path deliberately mirrors the older one's order of operations. Where the logic is shared, the
backends **cannot disagree**; where it isn't, a QA rule stands guard.

The developer tools that *do* pixel-diff still exist — but they're demoted to **aids, not gates**.
They help me localise "why does this look different?" during development; they never decide whether
something ships. That distinction — between a tool that assists and a tool that gates — turned out
to be one of the more important ones on the project.

## "Rule first, then fix"

The same discipline shaped how we handled defects reported by the team receiving our output. The
instinct is to jump straight to a fix. Instead, the order was:

1. A defect is reported on a converted asset.
2. It's **codified as a QA rule first** — and the rule is proven to *pass on good output and fire
   on the flawed output* **before any fix is written.**
3. *Then* the converter is fixed until the rule goes green.
4. The asset is re-checked.

```
defect report ──▶ write QA rule ──▶ prove it fires on the bad output
                                          │
                                          ▼
                                    fix converter ──▶ rule passes ──▶ re-QA
```

It feels slower. It's the opposite. Every fixed defect leaves behind a permanent regression test,
so the same bug can't come back quietly, and "fixed" means "provably fixed" rather than "looks
fixed on the one asset I checked." It also keeps the human review loop honest: the reporter and I
are arguing about a rule, not about a vibe.

## The unexpected dividend

Because the gate re-derives its expectations independently, it doesn't actually care who produced
the USD. That made it **producer-agnostic**: it can validate output from a *different* pipeline
entirely — which turned it from a one-project verifier into something with a life beyond the
project.

## What it demonstrates

The lesson I keep from this one is about **choosing the right oracle**. "Match the old output" is
a seductive definition of correct that quietly rots. "Satisfy an independent set of
consumer-facing rules that re-derive their own expectations" is more work to build and far more
honest — and it's what let two very different implementations converge on the same truth.
